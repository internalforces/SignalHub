# Review — PR #6 M3 Design and Roadmap

**Date:** 2026-08-04
**Scope:** Remaining unresolved review threads on PR #6 at `8a392d3`
**Verdict:** Addressed in the proposed design; human approval remains required before implementation.

## Addressed findings

1. Added an opaque, per-source storage metric namespace and a public-output projection so CSV, renamed sources, prior configurations, and current sources cannot combine persisted series.
2. Required source-atomic point and signal persistence, while retaining the explicitly documented cross-source partial-result behavior.
3. Made the JSON failure contract exhaustive for usage, configuration, selection, first-source, and later-source fetch/pipeline failures.
4. Added a CoinGecko contract-and-approval prerequisite covering endpoint, horizon, observation count, and timestamp semantics.
5. Chose one unbucketed duplicate-timestamp policy: fail the source with `duplicate_timestamp`; do not also skip it as a malformed record.
6. Corrected the bucket rule so a bucket ending exactly at the injected current time is closed and included.
7. Required manual redirect handling and target validation at every REST redirect hop.
8. Retained secret-safe output rules: interpolation remains whole-value and header-only, and failure codes are redacted classifications.

## Follow-up findings addressed

1. Revised values for an already persisted metric/timestamp are now an explicit `historical_conflict`, not an ignored update; the source transaction rolls back.
2. Redirects must remain on the configured origin, so request headers cannot be forwarded to a different origin.
3. Public signal-ID projection preserves every detector-configuration tuple item and replaces only the private metric-ID tuple item.

## Second follow-up findings addressed

1. M3 `run` uses its own fixed SQLite file, preventing a CSV metric string from colliding with or impersonating M3 storage.
2. The public Signal-ID example now uses the same JSON-serialized tuple encoding required by the projection contract.
3. Display metric IDs may overlap across distinct sources; the unique source ID supplies the persistent namespace, and the config package rejects only duplicate source IDs.

## Proactive follow-up findings addressed

1. Shared display metric IDs could still yield identical public signal IDs after private-metric projection. M3 output IDs now prepend the unique source ID while preserving detector configuration and the public metric ID.
2. The prior duplicate policy was exact only for the generic REST connector. Every provider contract must now define a deterministic reducer or a source failure for records that normalize to the same output timestamp, and connectors must return no duplicate points to Core.
3. The per-source atomicity requirement is reconciled with the no-schema-change gate: TASK-M3-6 may add only the storage-internal transaction boundary required by Core; any schema, shared-contract, or broader API change requires a focused proposal.
